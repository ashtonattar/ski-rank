# Slope Battles (ski-rank) — Project Status

> Living document. Update this file whenever meaningful changes are made to the app (features, fixes, architecture decisions). Keep the "Recent Work" section current and prune it periodically into a summarized history further down.

## Overview

- **App name:** Slope Battles — Freestyle Trick Duels
- **Repo:** `ashtonattar/ski-rank` (GitHub), single `main` branch
- **What it is:** A web app for freestyle skiers/snowboarders to log 1v1 trick "duels," get judged/scored live, and build a competitive ranking (ELO-style rating, tiers, badges, leaderboards, tournaments).

## Tech Stack & Architecture

- **Entirely client-side, single-file app:** all HTML/CSS/JS lives in `index.html` (~11,700 lines). No build step, no bundler, no `package.json`.
- **Backend:** Firebase (via CDN, `firebase-*-compat.js` v9.23.0)
  - **Firestore** — primary data store and real-time sync.
    - `state/global` doc — rankings, profiles, tournaments, chat, invites, etc. Written via a debounced full-document `.set()` (see `save()`/`_saveToFirestore()`).
    - `liveGames/{gameId}` collection — one doc per active/finished 1v1 match (split out from the global doc — see "Architecture decisions" below). Written via `saveLiveGame()`; `gameId` is the id of the invite that started the game.
  - **Firebase Auth** — email/password sign-in, plus a local/guest mode fallback (password hash stored when no Firebase UID).
  - **Firebase Storage** — stores uploaded trick clips.
- **Local dev server:** `python3 -m http.server 3400` (config in `.claude/launch.json`).
- **`.env`:** holds `GITHUB_TOKEN` (gitignored) — used for repo/deploy tooling, not consumed by the app itself.
- Firebase web API key is intentionally hardcoded client-side in `index.html` (~line 3345) — normal for Firebase web apps; security boundary is Firestore rules, not key secrecy.

## Core Features

- **Auth:** sign in / sign up / guest mode, nav bar reflects auth state.
- **Trick builder:** pick trick components by category (Grabs, Spins, Flips, etc.) and difficulty.
- **Live 1v1 games:** setup screen, optional neutral judge invite, pick-setter vote phase, dispute phase, forfeit-on-abandon, judge/player-left screens, reconnect handling via Firestore snapshots + a polling fallback.
- **Rating system:** ELO-style `calcRatings()` — upset wins (lower-rated player beats higher-rated) get boosted rating change (1.4×), expected wins get dampened (0.6×). This now fires automatically on every game based on pre-game ratings alone, independent of whether handicap mode was used for the match (previously it only fired inside explicit handicap-mode games — see Recent Work).
- **Tiers & badges:** skill tiers (e.g. "Developing" = 4.00–6.99 rating) with modal displays, badge unlocks.
- **Rankings/leaderboard:** weekly + all-time, filterable by sport (skier vs. boarder).
- **Profiles:** stats, rating history chart, paginated game history (10/page).
- **Social:** friends list/requests, direct chat with unread badges, explore feed (video clips, comments, swipe navigation), invite-a-friend links (`?ref=` deep link) for growing the userbase outside existing accounts.
- **Tournaments:** bracket and round-robin formats.
- **Challenges:** head-to-head challenge/invite flow.
- **Admin dashboard:** stats, users, games, ratings, raw data panels.
- **Mobile polish:** iOS Safari keyboard/safe-area fixes, per-tab scroll position persistence.

0zzzc. **Fixed the real cause of persistent "Cloud sync failed — Missing or insufficient permissions" errors on every save (chat, live games, everything) for certain accounts, surfaced right after the 0zzz1 fix stopped masking it as a chat-unread loop.** Console showed `Firestore save error: FirebaseError: Missing or insufficient permissions` from `_saveToFirestore` alongside repeated `Live game save error` from `saveLiveGame` (`index.html` ~4338) — both rules require `request.auth` to be non-null (`isSignedIn()`/`request.auth.uid` checks in `firestore.rules`), and both failing together on a normal (non-guest) signed-in account meant there was no real Firebase Auth session at all, despite the app believing it was signed in. Root cause: `doLogin()`'s legacy-account silent-migration path (~4692-4736) calls `_fbAuth.createUserWithEmailAndPassword()` to upgrade a pre-Firebase-Auth account; if that succeeds but the following Firestore `.update()` (writing `firebaseUid`, deleting `passwordHash`) fails (e.g. a network drop), the Firestore user doc still has `passwordHash` set, so *every future login* re-enters the same migration branch and immediately hits `auth/email-already-in-use` — and the old catch handler responded by falling back to a **local-only session** (`setSession()`+`launchApp()` with no real Firebase Auth sign-in) silently, every single time, forever. Every subsequent Firestore write for that account was therefore permanently doomed with no clear signal why. Fixed by recovering in that catch: on `auth/email-already-in-use`, actually call `_fbAuth.signInWithEmailAndPassword()` with the credentials just typed (the Firebase Auth account already exists from the earlier partial migration, so this succeeds) and finish the interrupted migration from there; only if that *also* fails does it fall back to a local-only session — and now with a visible toast explaining sync is off, instead of silent failure. Accounts already stuck in this broken state need to log out and back in once to pick up the fix. Not yet re-verified in-browser (no repro account available in this session).

Fixed by switching all three status-change sites (judge accept, player accept, decline) to `_updateArrayField('liveInvites', ...)` instead of the vulnerable full-doc write. 0zzz1. **Fixed the 0zzx toast-spam/stuck-unread fix not holding on accounts whose writes don't land (e.g. legacy/guest accounts without a real Firebase Auth session, hit by the rules' `isSignedIn()` check), or in a busy app where unrelated snapshots arrive before a mark-read write lands.** User reported that on another account, clicking an old (June 22) unread message still produced repeated "Cloud sync failed – changes saved locally" toasts, and the conversation still showed unread after clicking away. Root cause: the 0zzx fix guarded `openChat()`'s own passive re-invocation, but missed that the global `onSnapshot` handler (`index.html` ~3989) does `Object.assign(S, fresh)` on *every* incoming snapshot — including ones triggered by any other user's unrelated write — which blindly overwrites the whole `players` array, including the current user's in-memory `lastRead` map that `markRead()` had just set synchronously. If the corresponding Firestore write hadn't landed yet (still debouncing) or never lands at all (permission-denied), the very next snapshot reverted `lastRead`, making `getUnread()` positive again, so `openChat()`'s guard let `markRead()`/`save()` fire again — repeating the write→snapshot→revert→write loop indefinitely and re-triggering `_saveToFirestore`'s catch-block toast (~3860) each time. Fixed by applying the same snapshot-then-merge pattern already used for `liveInvites`/`tournaments` status (~3984-4008): snapshot the current user's `lastRead` before `Object.assign`, then after it, merge back per-friend keeping whichever timestamp (local vs. remote) is newer — a locally-set read timestamp can now never be reverted by a later unrelated snapshot, regardless of whether the underlying write ever succeeds. Doesn't fix the deeper issue of legacy/guest accounts being unable to persist read-state to Firestore at all (documented pre-existing limitation, `firestore.rules` ~66-70) — read state for such accounts now stays correct locally/on-device instead of flapping, but won't sync cross-device until the account migrates to real Firebase Auth. Not yet re-verified in-browser.
0zzx. **Fixed constant red "sync failed"/"conflict" toasts and messages staying marked unread after a refresh, both when receiving a friend chat message.** User reported that opening a conversation after receiving a message produced a steady stream of red toasts with SVG icon text, and that refreshing afterward still showed the conversation as unopened. Root cause: two places re-render an already-open chat passively whenever new data arrives — the global Firestore `onSnapshot` handler (`index.html` ~4046) unconditionally on *every* snapshot event, and the 3s message poll fallback (~11539) when message counts differ — and both did so by calling the full `openChat(_activeChatId, true)`, which unconditionally called `markRead()` → `save()` on every invocation regardless of whether anything was actually new. Since `save()` writes to the same `state/global` Firestore doc the `onSnapshot` listener watches, this created a tight write→snapshot→write feedback loop for as long as a chat stayed open: each write re-triggered the snapshot handler, which called `openChat()` again, which wrote again. This produced two symptoms at once — the repeated `_saveToFirestore()` calls' safety-guard/error paths (`index.html` ~3802, ~3860) fired their `<svg>`-icon-bearing red toasts repeatedly since the loop kept hitting them, and the perpetually-resetting 500ms save debounce (`save()`, ~5649) meant the one write that actually mattered (marking the conversation read) kept getting starved and could still be pending — or lost — when the user refreshed. Fixed by guarding the `markRead()` call in `openChat()` (~9038) with `if (getUnread(friendId) > 0)` — `markRead()` updates `me.lastRead` in-memory synchronously, so the first real call (user opening the chat, or the first passive refresh after a new message) marks it read and writes once, and every subsequent passive refresh triggered by the loop now sees zero unread and skips `markRead()`/`save()` entirely, breaking the loop at its source rather than patching either symptom individually. **Verified in-browser**: monkeypatched `save()` to count calls, seeded a fake unread message, called `openChat()` once (1 save, as expected) then 10 more times in a row simulating the passive-refresh loop (0 additional saves, `getUnread()` confirmed 0) — matching the fix's intent exactly.

0zzs. **Fixed the live-game dispute phase sometimes getting permanently stuck with both players' votes already cast.** Root cause: `_disputeResolved` (`index.html` ~3719) is a single per-tab boolean meant to stop a client from re-attempting a dispute resolution it already handled, but it was only ever reset back to `false` inside `enterDisputePhase()` (~7436) — which runs solely on whichever player's own click *made* the call. ## Architecture decisions

- **2026-07-28 — Live games split into their own Firestore doc.** Previously the entire app (players, games, tournaments, messages, *and* the currently-active 1v1 match) was one `state/global` doc, saved via a full-document `.set()` on every change. This meant the whole app could only support **one live game at a time, globally**, and any two users writing within the same ~500ms window (e.g. one submitting a dispute vote while another posts an explore comment) could clobber each other — the actual root cause behind several of the bug-fix commits above (rankings showing "undefined", tournament status reverting, invite status flipping back to pending).
  - Fix: `S.live` is now backed by `liveGames/{gameId}` (`gameId` = the id of the invite that started the match). `save()` auto-routes `S.live` there via `saveLiveGame()`; the ~12 gameplay functions (`setterSubmitTrick`, `voteForSetter`, `judgePickSetter`, dispute handlers, `finishLive`, etc.) were untouched since they all go through the same `save()` entrypoint.
  - New/changed functions: `subscribeLiveGame(gameId)` / `unsubscribeLiveGame()` (dedicated per-game `onSnapshot` listener, replacing the live-game logic that used to live inline in the global listener), `_tryResumeLiveGame()` (resumes the right game after reload/relogin by reading `gameId` off an accepted invite in `S.liveInvites`, which still lives on the global doc), `saveLiveGame(liveObj, immediate)`.
  - Multiple concurrent live games across different pairs of users are now possible for the first time (previously impossible by construction).
  - **Fixed 2026-07-31:** the dispute-flow double-resolve race (see 0zm above) — `resolveDisputeIfReady()` now claims the resolution via a Firestore transaction (`disputeClaimed` field on the live doc) before applying it, so only one of the two racing clients actually resolves a dispute and calls `finishLive()`. `_gameOverDismissed`/`_abandonHandled` remain local, unsynced flags, but their races are lower-risk (`_abandonHandled` only ever applies to a single "other player" in a 2-player match — no second racing client exists to double-apply it; `_gameOverDismissed` only gates local UI dismissal, not shared state). The identical pattern in `resolveSetterVoteIfReady()` (same dual-call-site shape as the dispute flow had) is unfixed — lower blast radius since it only affects who sets first, not ratings — flagged as a follow-up candidate.
  - **Fixed 2026-07-28:** `voteForSetter()` (the "who sets first" vote) had the same class of bug the dispute-phase fix (`54ae785`) addressed — it only resolved from the vote-casting client's own click handler, so two near-simultaneous votes could leave the game stuck on the vote screen. Fixed the same way: votes now write via a targeted `setterVotes.{uid}` field update instead of a full save, and resolution was extracted into `resolveSetterVoteIfReady()` (guarded by `_setterVoteResolved`), called both from `voteForSetter()` and from the live-game snapshot handler. Verified in the same two-tab test — both players voting simultaneously for the same option now resolves instantly with no nudge needed.

- **2026-07-28 — Chat messages fixed to use atomic writes; `_saveToFirestore()` now merges instead of overwriting.** Found while testing the Friends tab: two users messaging within ~1s of each other could lose one or both messages, same root cause as the live-game race (see above), just affecting `messages` on the shared `state/global` doc instead.
  - Fix: `sendMessage()` now writes new messages via `firebase.firestore.FieldValue.arrayUnion()` — atomic on Firestore's side, so it can't be clobbered by a concurrent write. `_saveToFirestore()` excludes `messages` (and `live`) from the regular debounced full save, and the write itself changed from `batch.set(docRef, copy)` to `batch.set(docRef, copy, { merge: true })` — so omitting a field now leaves it untouched server-side instead of deleting it.
  - **Fixed 2026-07-31:** `friendRequests` and `challenges` (see 0zo) — creates now go through `arrayUnion`, status changes/removals go through a new `_updateArrayField()` transaction helper, and both fields are excluded from the general save. `pending` was already fixed previously (arrayUnion/arrayRemove via `submitLoggedGame`/`confirmGame`/`disputeGame`/`cancelPending`), despite once being listed here as unfixed. **Fixed 2026-07-31 (same session):** explore-feed `comments`/`likes` (see 0zp) — per-item dot-path `arrayUnion`/`arrayRemove`, both fields excluded from the general save. This closes out every field that shared this race class; no further known instances remain.

- **2026-07-28 — Tournament invite/participant race fixed.** Found while testing the Tourneys tab: accepting a tournament invite (or being added as a participant) could get silently reverted by an incoming Firestore snapshot arriving before the debounced write landed — same race class as live-game/messages, but `S.tournaments` had no merge protection at all (unlike `S.liveInvites`, which already guards against this).
  - Fix: in the global `onSnapshot` handler, added a merge step for `S.tournaments` mirroring the existing `S.liveInvites` guard — before overwriting state, snapshot each tournament's previous `invitees`/`participants`; after the overwrite, restore an invitee's `accepted`/`declined` status if the incoming snapshot regressed it to `pending`, and re-add any participant present locally but missing from the incoming snapshot.
  - **Verified 2026-07-28**: reproduced the tournament bug directly (mutate `participants`/`invitees` via the real `acceptTourneyInvite()` codepath, call `save()`, watch it revert within ~300ms), applied the fix, reran the identical repro — state now stays stable indefinitely, the UI correctly reflects the accepted participants, and starting the tournament generates the bracket correctly with no console errors.
